# 11. Knowledge Plane: Code Intelligence for Impact & Invalidation

> Part of the Multiverso research corpus - https://github.com/coagente/multiverso - Cutoff: 2026-08-12

## Why this matters for Multiverso

Multiverso's evidence plane binds evidence (test results, oracle receipts, adversarial challenges) to the exact state of a world. The moment trunk advances or a world mutates, some of that evidence is stale — and re-running everything against every candidate world burns the fixed budget that the scheduler is supposed to allocate intelligently. The knowledge plane is the machinery that answers three questions cheaply: *what did this change touch*, *what transitively depends on it*, and therefore *which evidence is invalidated and which oracles must re-run*. Industry has attacked exactly this problem for a decade under the names "impact analysis," "regression test selection," and "code indexing" — at Google, Meta, GitHub, Sourcegraph, Datadog, and Launchable — and the published numbers are strikingly consistent: the naive invalidation set (everything transitively affected) is roughly 100x larger than the set that matters ([Memon et al., ICSE-SEIP 2017](https://research.google.com/pubs/archive/45861.pdf)). That gap is Multiverso's budget headroom. The knowledge plane is explicitly **optional and post-MVP** in the architecture; this chapter's job is to establish what the cheap baseline buys, what each successively richer layer adds, and at what scale a Glean-style fact store actually pays for itself.

## State of the art

### Glean: typed facts and the Angle query language (Meta)

[Glean](https://github.com/facebookincubator/Glean) is Meta's open-source "system for collecting, deriving and working with facts about source code," BSD-licensed and hosted under facebookincubator. Its data model is a database of immutable, deduplicated **facts** organized into **predicates** (typed, schema-defined records — declarations, references, types, call edges, inheritance, imports) that form a DAG, stored on RocksDB. Both schemas and queries are written in **Angle**, a Datalog-style declarative logic language (an anagram of "Glean") that also supports *derived* predicates — including language-neutral views layered over language-specific facts, so a tool can ask "all declarations in this file" for any indexed language ([Meta engineering blog, 2024-12-19](https://engineering.fb.com/2024/12/19/developer-tools/glean-open-source-code-indexing/); [Angle guide](https://glean.software/docs/angle/guide/)).

Language coverage in the open-source release: first-class indexers for C++, Hack, Haskell, JavaScript/Flow, and Python; ingestion of **SCIP/LSIF** indexes covers Rust, Go, TypeScript, Java, Python and .NET; and a further set of Meta-internal indexers (Java, Kotlin, Erlang, Thrift, Buck/Bazel, C#, Swift) has **not** been open-sourced ([Glean README](https://github.com/facebookincubator/Glean)). Two design points matter most for Multiverso:

1. **Incremental indexing via stacked databases.** Glean achieves O(changes) rather than O(repository) re-indexing by stacking immutable fact databases — a base snapshot plus deltas ([Meta engineering blog](https://engineering.fb.com/2024/12/19/developer-tools/glean-open-source-code-indexing/)). This is structurally identical to what a per-world index overlay would need.
2. **One index, many consumers.** At Meta, Glean powers the Glass symbol server, code browsing, VS Code C++ navigation, auto-generated documentation, code review integration, and dead-code detection ([Meta engineering blog](https://engineering.fb.com/2024/12/19/developer-tools/glean-open-source-code-indexing/)).

**Maturity outside Meta:** thin. The project has ~1.4k GitHub stars and an active issue tracker ([GitHub](https://github.com/facebookincubator/Glean)), but the Hacker News discussion of the December 2024 post is blunt: the internal consumers (code review, IDE/LSP integration) are too coupled to Meta infrastructure to open-source, and "the lack of open source integrations are the main barrier for external adoption" ([HN thread](https://news.ycombinator.com/item?id=42568516)). There is no publicly documented production deployment of Glean outside Meta that this survey could verify. It is a Haskell codebase with a non-trivial build. The comparable Google system, **Kythe** (open-sourced 2015, descended from Steve Yegge's Grok), had its entire US-based development team laid off in April 2024 and moved to maintenance ([Wikipedia: Google Kythe](https://en.wikipedia.org/wiki/Google_Kythe)) — the "hyperscaler code-fact graph" category has effectively no healthy open ecosystem in 2026.

### SCIP and LSIF (Sourcegraph)

**LSIF** (Language Server Index Format, introduced via VS Code in 2019) serialized LSP responses into a static index. It is dead as a format: [lsif.dev](https://lsif.dev/) is archived and states plainly that "LSIF has been superseded by SCIP."

**SCIP** (SCIP Code Intelligence Protocol) was announced by Sourcegraph on June 8, 2022, after scaling problems with LSIF across 45,000+ indexed repositories and 4,000+ daily uploads. Design: Protobuf instead of JSON-graph, and — crucially — **human-readable, globally unique string symbol IDs** instead of LSIF's opaque numeric graph IDs, a schema "heavily inspired by SemanticDB." Reported wins: a 10x CI speedup replacing lsif-node with scip-typescript; gzipped indexes ~4x smaller; and Meta (which ingests SCIP into Glean) found SCIP payloads "8x smaller, and can be processed 3x faster" than LSIF ([Announcing SCIP](https://sourcegraph.com/blog/announcing-scip)).

The indexer ecosystem is the broadest of any precise-code-intel format: scip-java (Java/Scala/Kotlin), scip-typescript, scip-python, scip-clang (C/C++), scip-ruby, scip-dotnet, scip-dart, scip-php, and rust-analyzer emitting SCIP natively for Rust ([sourcegraph/scip README](https://github.com/sourcegraph/scip)). Because SCIP symbols encode **package + version + symbol name**, Sourcegraph ships genuine **cross-repository navigation**: go-to-definition into a dependency's repo and find-references across repo boundaries, version-aware; as of January 2026, 45,000+ of the 2.8M public repos on Sourcegraph.com have SCIP precise indexes ([Cross-repository code navigation, 2026-01-21](https://sourcegraph.com/blog/cross-repository-code-navigation)). For Multiverso, SCIP's significance is as the **lingua franca**: it is the one precise format that is produced by many independent indexers and consumed by multiple systems (Sourcegraph, Glean, the scip CLI).

### stack-graphs (GitHub): archived

GitHub's [stack graphs](https://github.blog/open-source/introducing-stack-graphs/) (announced December 9, 2021) were a serious attempt at a third architecture: declare a language's *name-binding rules* in a DSL layered on tree-sitter, build a per-file graph with no build-system integration, and resolve references by path-finding with a symbol stack — incremental (only changed files re-analyzed) and zero-config, based on the scope-graphs research of Eelco Visser's group at TU Delft. It shipped precise code navigation for Python (2021) and all TypeScript repositories ([GitHub changelog, 2024-03-14](https://github.blog/changelog/2024-03-14-precise-code-navigation-for-typescript-projects/)). Then GitHub **archived the repository on September 9, 2025**; it is read-only and explicitly "no longer supported or updated by GitHub" ([github/stack-graphs](https://github.com/github/stack-graphs)). The lesson is sobering: even with GitHub's resources, per-language binding rules were expensive to author and maintain, and the zero-config precise-navigation bet was abandoned. Multiverso should not build on stack-graphs, and should treat "we'll write our own name resolution" as a trap.

### tree-sitter: best-effort structure, not semantics

[Tree-sitter](https://tree-sitter.github.io/tree-sitter/) is a parser generator and incremental parsing library: fast enough to reparse on every keystroke, robust in the presence of syntax errors, dependency-free (C11 runtime), with ~25 first-party grammars and a large community grammar ecosystem. What it produces is a **concrete syntax tree** — and nothing more. GitHub's own stack-graphs post is the cleanest statement of the limit: parsing alone cannot resolve names; shadowing, imports, and binding rules are semantic and language-specific ([Introducing stack graphs](https://github.blog/open-source/introducing-stack-graphs/)). Tree-sitter gives you *where definitions and references syntactically occur*, not *which definition a reference resolves to*, and no types at all.

Its role in 2026 is nonetheless central to agent tooling: aider's repo map extracts symbol definitions/references with tree-sitter and runs a graph-ranking algorithm over the file-dependency graph to pack the most-referenced identifiers into a ~1k-token context budget ([aider repo map](https://aider.chat/docs/repomap.html); [blog, 2023-10-22](https://aider.chat/2023/10/22/repomap.html)). That is the correct framing for Multiverso: tree-sitter is a **cheap, always-available approximation layer** — good for candidate ranking, context packing, and heuristic impact hints; never a soundness source for invalidation.

### Impact analysis and predictive test selection: the numbers

This is the most directly transferable literature, because "which tests to re-run after a change" is exactly "which evidence is invalidated," approached from the cost side.

**Google TAP** ([Memon et al., ICSE-SEIP 2017](https://research.google.com/pubs/archive/45861.pdf)) is the canonical dataset. Scale: a ~2-billion-LOC monolithic repo, 13K+ projects, and on an average day **800K builds and 150 million test runs**. TAP computes AFFECTED test targets by walking **reverse dependencies in the Bazel BUILD graph** from changed files, batching commits into "milestones" cut every ~45 minutes, with affected sets as large as **4.2 million test targets**. The empirical findings are the quantitative foundation for any invalidation design:

- Of **5.5 million** unique affected test targets over one month (500K+ changelists, 4B+ test outcomes), only **~63K ever failed**; 91.3% passed at least once and *never* failed.
- After filtering flakes, only **1.23%** of executed targets ever surfaced a real breakage or fix; the PASSED:FAILED ratio per change is ~**99:1**.
- Test targets more than **~10 dependency edges** away from the changed file "hardly ever break"; real breakages concentrate at dependency distance 5–10.
- Files modified by **3+ developers** in a short window are significantly more breakage-prone.

**Meta's predictive test selection** ([Machalica, Samylkin, Porth, Chandra — arXiv:1810.05286](https://arxiv.org/abs/1810.05286), deployed in production) takes the next step: a gradient-boosted decision-tree model trained on historical test outcomes selects a subset of the transitively-affected tests per change. Results: **infrastructure cost of testing halved**, while catching **>95% of individual test failures** and **>99.9% of faulty changes**, running about **a third** of the tests that transitively depend on modified code ([Meta engineering blog, 2018-11-21](https://engineering.fb.com/2018/11/21/developer-tools/predictive-test-selection/)). Note the two recall numbers: learned selection *does* miss individual failures (5%), and only change-level recall stays near-perfect. A 2025 replication study at TU Wien examined the approach outside Meta ([Aichmann, Predictive Test Selection: A Replication Study](https://repositum.tuwien.at/bitstream/20.500.12708/215633/1/Aichmann%20Stefan%20-%202025%20-%20Predictive%20Test%20Selection%20A%20Replication%20Study.pdf)).

**Commercial products.** [Launchable](https://www.cloudbees.com/newsroom/cloudbees-acquires-launchable-to-boost-genai-efforts-across-devsecops) (founded 2019 by Jenkins creator Kohsuke Kawaguchi and Harpreet Singh) productized ML-based predictive test selection; customers including BMW and GoCardless reported 50% machine-hour and up to 90% test-execution-time reductions; CloudBees acquired it on August 7, 2024. [Datadog Test Impact Analysis](https://docs.datadoghq.com/tests/test_impact_analysis/) (formerly "Intelligent Test Runner") takes the *coverage-map* approach rather than ML: it transparently collects **per-test code coverage**, maps each test to the files it executes, and skips tests whose covered files didn't change. Its documented caveats are a checklist of invalidation blind spots: it cannot see changes to library dependencies, compiler options, external services, or data files unless those are explicitly declared "tracked files"; it uses Bloom filters with ~0.04% false-positive matching; and it bails out on commits touching 5,000+ files ([Datadog docs](https://docs.datadoghq.com/tests/test_impact_analysis/); [Datadog blog](https://www.datadoghq.com/blog/streamline-ci-testing-with-datadog-intelligent-test-runner/); their Ruby implementation reports ~50% testing-time savings — [Datadog engineering](https://www.datadoghq.com/blog/engineering/ruby-test-impact-analysis/)). The academic ancestor is **Ekstazi** ([Gligoric, Eloussi, Marinov, ISSTA 2015](https://github.com/gliga/ekstazi)): regression test selection from *dynamic file-level dependencies*, adopted in Apache Camel, CXF, and Commons Math.

### Build graphs as a knowledge source

Where a real build system exists, its dependency graph is the cheapest *sound over-approximation* available. Bazel's query language answers reverse-dependency questions directly — `rdeps(universe, targets)` and Sky Query's `allrdeps` ([Bazel query guide](https://bazel.build/query/guide)) — and a small ecosystem computes changed-target sets between two commits: [bazel-diff](https://github.com/Tinder/bazel-diff) (Tinder; content-hash based, tested on tens-of-thousands-of-target graphs) and [target-determinator](https://github.com/bazel-contrib/target-determinator) (bazel-contrib). **Buck2**, Meta's Rust rewrite open-sourced April 2023, is built around a *single incremental dependency graph* with no phases and roughly 2x Buck1 performance internally; its **BXL** (Buck Extension Language, Starlark) lets scripts query the unconfigured/configured/action graphs programmatically ([Meta engineering blog, 2023-04-06](https://engineering.fb.com/2023/04/06/open-source/buck2-open-source-large-scale-build-system/); [Tweag's Buck2 tour](https://www.tweag.io/blog/2023-07-06-buck2/)). TAP is the existence proof that build-graph rdeps alone is a workable invalidation oracle at the largest scale on earth — and its 99:1 waste ratio is the proof that it is a *loose* one.

### The MVP-sufficient baseline

Putting the above together, the baseline Multiverso can ship without any knowledge plane infrastructure:

1. **Touched files** from the world's diff (free — Git gives it).
2. **grep/ripgrep** for textual reference candidates (unsound both directions, but instant).
3. **LSP on demand** inside the world's container (definitions/references from the same language servers the agent already runs).
4. **SCIP-when-available**: run scip-typescript/scip-python/scip-java/rust-analyzer in CI per admitted trunk snapshot; store the index in CAS.
5. **Build-graph rdeps** when the repo uses Bazel/Buck2 (bazel-diff-style changed-target sets).
6. **Per-test coverage maps** (Datadog-style): which files does each test execute — collected once per trunk snapshot, invalidated by touched files.
7. **Dynamic traces** from oracle runs already captured by the evidence plane.

Each layer is an independent, droppable heuristic; the union is a conservative invalidation set and the intersection is a prioritization signal.

## Implications for Multiverso design

1. **Treat invalidation soundness as a first-class label on evidence.** Every mechanism surveyed sits somewhere on a soundness/cost frontier: build-graph rdeps is a sound over-approximation (given honest BUILD files), coverage maps are near-sound for code changes but blind to dependency/config/external changes ([Datadog's own caveat list](https://docs.datadoghq.com/tests/test_impact_analysis/)), grep and tree-sitter are unsound in both directions, and learned selection is explicitly lossy (95% per-test recall at Meta). Attestations should therefore record the **invalidation basis** — "this evidence was deemed fresh under coverage-map invalidation" is a materially weaker claim than "fresh under full re-execution," and the Decision stage should be able to price that difference.

2. **Selection for scheduling, over-approximation for admission.** The Meta numbers imply a clean division: use predictive/learned signals to decide *what to run first* under budget (raising true-positive yield per compute unit — exactly Multiverso's core research question), but never let a <100%-recall selector be the only thing standing between a candidate and admission. A cheap final policy: the winning world re-runs its build-graph-affected set (sound) once before ADMIT, while losing worlds only ever got selective evidence.

3. **Standardize on SCIP as the semantic interchange; defer Glean.** SCIP indexes are produced by maintained third-party indexers for the mainstream agent languages (TS/JS, Python, Java/Scala/Kotlin, Rust, Go via lsif-go lineage, C++), are compact protobuf artifacts that slot naturally into Multiverso's CAS keyed by snapshot hash, and are consumed by both Sourcegraph and Glean — so adopting SCIP now keeps a Glean upgrade path open ([Announcing SCIP](https://sourcegraph.com/blog/announcing-scip); [Glean README](https://github.com/facebookincubator/Glean)). The stack-graphs archive and Kythe's 2024 gutting are warnings against betting on any single vendor's precise-indexing runtime; a *format* is a safer dependency than a *service*.

4. **The MVP baseline is genuinely sufficient — TAP proves the ceiling is low.** Google ran (and still runs) planet-scale invalidation on nothing more semantic than BUILD-file reverse dependencies plus history heuristics ([TAP paper](https://research.google.com/pubs/archive/45861.pdf)). Multiverso's MVP repos are orders of magnitude smaller. Touched files + build graph (when present) + per-test coverage maps + SCIP-when-available answers "which evidence is stale" conservatively at near-zero infra cost. The one component worth building early is the **per-test coverage map per trunk snapshot**, because it converts invalidation from target-granularity to evidence-granularity — the same move Datadog sells.

5. **When does a Glean-style fact store pay for itself?** The break-even has three drivers, none of which is raw LOC alone: (a) **query volume** — when the scheduler, N concurrent worlds, and agent context-packing all hit "who calls X / what depends on Y" many times per decision, on-demand LSP (seconds, per-world process) loses to a pre-computed index (milliseconds, shared); (b) **fan-out across worlds** — a shared base index with per-world deltas amortizes indexing across all candidates, and Glean's stacked-database design is precisely this shape ([Meta engineering blog](https://engineering.fb.com/2024/12/19/developer-tools/glean-open-source-code-indexing/)); (c) **cross-language/cross-repo edges** (Thrift/Protobuf ↔ generated code, service boundaries) that neither LSP nor per-repo SCIP sees. Concretely: below ~10 concurrent worlds on a single-language mono-repo, the baseline wins; a Glean/Angle-class store becomes rational when Multiverso operates as a persistent service over a large multi-language estate where symbol-level invalidation queries are the scheduler's inner loop. Even then, the operational cost of Glean-outside-Meta (Haskell build, no OSS integration ecosystem — [HN](https://news.ycombinator.com/item?id=42568516)) suggests building the fact store *on ingested SCIP + build graph + coverage facts* rather than adopting Glean wholesale.

6. **Steal the derived-predicate idea regardless of backend.** Angle's key trick — language-neutral views derived over language-specific facts — is exactly what "which evidence is stale?" needs: a single `staleness(Evidence, Change)` predicate derived from heterogeneous sources (build edges, coverage edges, SCIP references, trace edges). Even a SQLite/Datalog-lite implementation of that schema keeps the decision logic clean and lets backends upgrade underneath.

## Open questions

- **Recall accounting under composition.** If evidence from selective invalidation feeds a COMPOSE decision merging two worlds, how do per-mechanism recall losses compound, and can the attestation carry a computed lower bound on effective recall?
- **World-delta indexing latency.** Can SCIP indexers (built for CI snapshots) be run incrementally enough for short-lived worlds — or is tree-sitter-diff + LSP the only viable in-world layer, with precise indexes reserved for trunk snapshots? No published system indexes speculative branches at world-creation rates.
- **Learned selection without history.** Meta/Google/Launchable all train on years of test-outcome history. A young Multiverso deployment has none. Do TAP-style structural priors (dependency distance ≤10, change-author fan-in) transfer as a cold-start policy, and can outcomes from *rejected worlds* — which ordinary CI never sees — make training data richer per commit?
- **Adversarial invalidation.** All surveyed systems assume changes are honest. A candidate world produced by an agent could (accidentally or through reward hacking) shape a change to *minimize* its apparent impact set (e.g., reflection, dynamic imports — the known blind spots of coverage-based selection). Does admission-grade invalidation need the challenge plane to specifically attack the impact computation?
- **Knowledge plane as agent context vs. invalidation oracle.** The same index serves both the scheduler (invalidation) and generation agents (context, à la aider's repo map). Are the freshness requirements different enough that they need separate consistency levels over the same facts?
