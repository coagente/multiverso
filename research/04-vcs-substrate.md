# 4. VCS Substrate: Jujutsu, GitButler, Patch Theory & Structural Merge

> Part of the Multiverso research corpus - https://github.com/coagente/multiverso - Cutoff: 2026-08-12

## Why this matters for Multiverso

Multiverso is a control plane, not a VCS. It spawns N candidate worlds per intent, binds evidence to each world's exact state, and admits one integrated state to trunk as an ordinary Git commit plus a signed attestation. Every one of those verbs — spawn, snapshot, compose, admit — bottoms out in a version-control substrate. The design question for this chapter is narrow but load-bearing: **which substrate primitives genuinely help a candidate-race control plane, which are irrelevant, and where is the boundary between "representable inside Git" and "needs an external ledger"?**

Three developments since 2024 make this a live question rather than a settled one. First, Jujutsu matured into the most credible Git-compatible engine with primitives (operation log, first-class conflicts, stable change identity) that look tailor-made for speculative multi-world workflows — while remaining explicitly experimental. Second, GitButler pivoted its entire product toward agent workflows, shipping an agent-oriented CLI and session-to-branch attribution, and even published benchmarks of how well agents drive different VCSs. Third, structural merge went from research curiosity to deployable tooling (Mergiraf, weave, gfix), giving Multiverso's COMPOSE decision a real mid-layer between textual merge and agent repair. Getting the adapter layer right — and refusing to rebuild any of this — is the difference between a research prototype and a system teams can adopt on day one.

## State of the art

### Jujutsu (jj): the most interesting substrate, still experimental

Jujutsu is a Git-compatible VCS whose README states plainly: "Jujutsu is an **experimental version control system**. While Git compatibility is stable, and most developers use it daily for all their needs, there may still be work-in-progress features, suboptimal UX, and workflow gaps that make it unusable for your particular use" ([jj README](https://github.com/jj-vcs/jj)). It also states "Today, only the Git backend is production-ready" and — despite the lead developer working on it full-time at Google — "this is not a supported Google product" ([jj README](https://github.com/jj-vcs/jj)).

The primitives that matter for a control plane:

- **Working-copy-as-commit.** The working copy is itself a commit that is amended on every snapshot; there is no staging area or stash. Every state an agent produces is automatically a commit-shaped object ([jj README](https://github.com/jj-vcs/jj)).
- **First-class conflicts.** Merges and rebases *never* stop the world: "the conflict will be recorded in the rebased commit and the rebase operation will succeed." Conflicted commits can themselves be rebased, merged, and edited; conflicts support arbitrarily many sides (Git-style markers only render 2-sided conflicts, falling back to snapshot style beyond that) ([jj conflicts docs](https://docs.jj-vcs.dev/latest/conflicts/)).
- **Auto-rebase.** Rewriting a commit automatically rebases all descendants, and conflict resolutions propagate to descendants — no `--continue` babysitting ([jj conflicts docs](https://docs.jj-vcs.dev/latest/conflicts/)).
- **Operation log.** Every repo-mutating command is recorded with a "view" snapshot (bookmarks, refs, heads, working-copy commits per workspace) plus metadata (timestamp, user, hostname). This enables sequential `jj undo`/`redo`, `jj op restore` to any prior state, and **lock-free concurrency**: concurrent commands cannot corrupt the repo; conflicting concurrent edits surface as *divergence* to be resolved, not corruption ([jj operation log docs](https://docs.jj-vcs.dev/latest/operation-log/)).

**What lives in Git vs outside Git.** This boundary is exactly Multiverso's interop problem in miniature. Commits and file content are stored in the Git repository (via gitoxide). Conflicted commits *cannot* be represented in Git's object model, so jj writes placeholder root directories (`.jjconflict-base-*/`, `.jjconflict-side-*/`) whose "purpose … is only to prevent GC of the relevant trees; the authoritative information is in a non-standard `jj:trees` commit header." Change IDs (stable identity across amendments) are stored in a non-standard Git commit header that survives some rewrites (`commit --amend`) but not others (rebases), though "major forges generally preserve the header." Bookmarks, and the entire operation log, live in jj's own storage outside the Git repository ([jj git-compatibility docs](https://docs.jj-vcs.dev/latest/git-compatibility/)). Lesson: even jj, with maximal Git-compatibility ambitions, needed a side-ledger for its control-plane state.

**Governance and maturity.** Jujutsu has a formal governance document: maintainers are nominated from active contributors and voted in; proposals get a 2–4 week discussion window with majority-of-participating-votes acceptance; and — notably for a project whose founder works at Google — "At most 1/3 of the maintainers may be paid for their contributions by a single company," with nine maintainers listed as of this writing ([jj governance](https://docs.jj-vcs.dev/latest/governance/governance/)). Releases are monthly 0.x minors: 0.44.0 shipped 2026-08-05 (stabilized tag fetch/push), 0.43.0 on 2026-07-01 introduced `jj run` — executing commands across multiple changes with private working copies, a primitive directly relevant to oracle execution over candidate sets ([jj changelog](https://docs.jj-vcs.dev/latest/changelog/)). Colocated Git repositories became the default in 0.34.0 (2025-10-01), and sequential undo/redo landed in 0.33.0 ([jj changelog](https://docs.jj-vcs.dev/latest/changelog/)). The `jj-lib` Rust crate is published in lockstep (0.44.0, 2026-08-06) but the project is pre-1.0 and ships breaking changes at each minor; no library API stability commitment is documented ([jj-lib on docs.rs](https://docs.rs/jj-lib/latest/jj_lib/), [jj changelog](https://docs.jj-vcs.dev/latest/changelog/)). Building Multiverso's core *on top of* jj-lib would chain the project to an unstable API; driving `jj` as a CLI adapter is the defensible integration.

### GitButler: agent sessions as a product

GitButler is a Git client (Tauri/Rust/Svelte) built around **virtual branches**: multiple branches applied simultaneously to one working directory, unified by a special `gitbutler/workspace` merge commit so ordinary Git tooling sees one coherent state ([GitButler repo](https://github.com/gitbutlerapp/gitbutler), [Trigger.dev on GitButler](https://trigger.dev/blog/parallel-agents-gitbutler)).

Since late 2025 the company has aggressively repositioned for agents:

- **Agents Tab (2025-09-11).** Claude Code sessions run inside the client, "tied to branches of your project, automatically committing the results of finished tasks to that branch." Each branch keeps an independent agent context; the UI shows transcripts, per-branch token usage and cost estimates, and diffs; commit messages are generated "using your prompts for proper context" ([GitButler Agents Tab post](https://blog.gitbutler.com/agents-tab)).
- **The `but` CLI (2026-02-05, technical preview).** Agent-oriented commands: `but commit` with positional file/hunk IDs (commit *these hunks* to *that branch*), `but amend`, `but absorb`, `but squash`, `but uncommit`, `but pr`, `but land` (direct landing "with explicit authorization"), and `but oplog` for undo/restore of prior GitButler states. All commands emit JSON via `-j`; `but agent setup` is a wizard that installs a skill and version-control instructions for the agent ([Introducing the GitButler CLI](https://blog.gitbutler.com/but-cli), [GitButler AI agents docs](https://docs.gitbutler.com/ai-agents/overview)).
- **Session→branch routing.** For parallel agents, "the agent uses GitButler to commit the changes for its task to its GitButler branch" — attribution of hunks to sessions is handled by the platform plus agent discipline, not by filesystem isolation. GitButler's own docs are candid about the limit: parallel agents share "one filesystem, dependency install, generated files, and app state," and users should fall back to worktrees when agents need incompatible checkout states ([GitButler parallel agents docs](https://docs.gitbutler.com/ai-agents/parallel-agents)). Trigger.dev's field report (2026-04-16) documents both the win (no more worktree-management scripts, port conflicts, 9.8 GB duplicated checkouts) and the failure modes: same-file edits across branches create "races and interference" ([Trigger.dev](https://trigger.dev/blog/parallel-agents-gitbutler)).
- **vcbench (2026-07-07).** GitButler's cofounder built vcbench.dev: 300 runs, two coding agents, five history-manipulation tasks (selective commit, multi-amend, split, reorder, squash), graded by a deterministic script on the final Git state. Headline claim: "GitButler ran about 60% faster than git with roughly 80% fewer commands while Jujutsu ran slower than git" ([Agentic Version Control Benchmarks](https://blog.gitbutler.com/vcbench)). This is a vendor benchmark of *history manipulation*, not of candidate racing or verification — but it is the first quantitative evidence that VCS interface design measurably changes agent token/latency cost.
- GitButler raised a $17M Series A "to build what comes after Git" (2026-04-08) ([GitButler Series A](https://blog.gitbutler.com/series-a)).

### Sapling, Pijul/Darcs, Fossil: three other answers

**Sapling (Meta).** The `sl` CLI is open source and can clone Git/GitHub repos; the Mononoke server and EdenFS virtual filesystem run in production at Meta but "are not yet supported for external usage." Meta's deployment "scales to repositories with 10's of millions of files, commits, and branches," and the docs admit the design "geared towards corporate, always-online, single-master, rebase-instead-of-merge, monorepo environments" ([Sapling introduction](https://sapling-scm.com/docs/introduction/), [sapling repo](https://github.com/facebook/sapling)). Sapling has two repo formats — `.git` mode (Git-command interop, with caveats like "mixing `sl` and `git` commands might not work in all cases") and `.sl` mode (unlocks EdenFS and scale features, no Git commands) ([Sapling Git support modes](https://sapling-scm.com/docs/git/git_support_modes/)). Sapling's UX innovations (smartlog, `absorb`, first-class stacked commits, commit-cloud backup of *every* commit as created) are relevant patterns; its server-side stack is not adoptable.

**Pijul and Darcs (patch theory).** Darcs (v2.18.5, January 2025, still maintained under Software Freedom Conservancy) models a repository as a set of patches rather than snapshots ([darcs.net](https://darcs.net/)). Pijul (~1.0.0-beta) is the modern successor: a "mathematically sound theory of patches" where independent changes "can be applied in any order without changing the result or the version identifier," order between lines is always preserved (unlike 3-way merge), and "once resolved, conflict resolutions applies to the same two changes everywhere" ([pijul.org](https://pijul.org/)). Pijul's key theoretical fix over Darcs: "Conflicting changes always commute in Pijul and never commute in Darcs" — eliminating Darcs' pathological merge behavior ([Pijul FAQ](https://pijul.org/faq)). Commutation is the theoretically ideal property for a system that admits candidate changes in scheduler-chosen order. But Pijul's hosting platform (the Nest) is "still at an experimental stage" ([Pijul FAQ](https://pijul.org/faq)), the ecosystem is tiny, and none of it interoperates with Git-native forges, CI, or agent tooling. Patch theory is a design lodestar for Multiverso's SERIALIZE/COMPOSE semantics, not a substrate choice.

**Fossil.** Fossil stores an entire project — code, wiki, tickets, forum — as an unordered set of immutable artifacts in a single SQLite file; "the entire project history can be reconstructed simply by scanning the artifacts in an arbitrary order," and this artifact set is the "global state" synced between peers ([Fossil tech overview](https://fossil-scm.org/home/doc/trunk/www/tech_overview.wiki), [Fossil file formats](https://fossil-scm.org/home/doc/trunk/www/fileformat.wiki)). Fossil is the strongest existing precedent for Multiverso's instinct that *process artifacts* (intents, decisions, evidence records) belong in the same replicated, content-addressed store as the code — while simultaneously demonstrating the adoption cost of not being Git.

### Unison: content-addressed code, and why it doesn't transfer

Unison, which reached 1.0 on 2025-11-25 ([Unison blog](https://www.unison-lang.org/blog/)), identifies every definition "by a hash of its syntax tree" (512-bit SHA-3, with argument names positionalized and dependencies replaced by their hashes); "names are just separately stored metadata that don't affect the function's hash," and the codebase lives in a managed database rather than text files ([Unison: the big idea](https://www.unison-lang.org/docs/the-big-idea/)). Consequences: perfect incremental compilation, renames that can't conflict, and multiple versions of a definition coexisting because they are literally different hashes.

Why this doesn't transfer to Multiverso's polyglot reality: the model requires that (a) the language's semantic unit is a well-defined, normalizable AST node, (b) *all* dependencies are themselves content-addressed in the same system, and (c) the toolchain agrees to treat the database, not text, as the source of truth. Real repositories are polyglot mixtures of code, build scripts, configs, migrations, and binary assets whose identity is file- and line-based, whose toolchains parse text, and whose ecosystems (LSP, CI, review) assume Git. The transferable lesson is narrower: **content addressing at the right granularity eliminates whole classes of conflicts and makes caching sound** — which is why Multiverso content-addresses snapshots and evidence (CAS in the data/evidence planes) even though it cannot content-address *definitions*.

### Mergiraf and the structural merge layer

Mergiraf is the reference implementation of practical structural merge: a Git merge driver (also invocable post-hoc via `mergiraf solve`) supporting **31 programming languages and 12 declarative formats** ([mergiraf.org/languages](https://mergiraf.org/languages.html)). Its architecture is precisely documented ([mergiraf.org/architecture](https://mergiraf.org/architecture.html)):

1. **Fast path:** try line-based diff3 first; if conflict-free (and no duplicate-key check triggers), return it.
2. **Structural path:** parse all three revisions with tree-sitter (multi-line leaves split per line); match nodes across revisions with the GumTree algorithm (isomorphic top-down, then bottom-up, with stricter left↔right matching); build equivalence classes; convert trees to Parent-Child-Successor triples (3DM-style); union, detect inconsistencies, and resolve — including *commutative children* (e.g., import lists, unordered members) that can be reordered/merged conflict-free.
3. **Safeguards:** a delete-vs-modify check, and a duplicate-signature check that converts accidentally-duplicated declarations back into explicit conflicts.
4. **Fallbacks:** "if a parsing error occurs in any of the three revisions, the algorithm aborts and falls back on line-based merging"; remaining inconsistencies also fall back; and Mergiraf deliberately **retains conflict markers in suspicious cases** rather than over-resolving ([mergiraf.org](https://mergiraf.org/)).

Critically, Mergiraf "makes no promises about syntactic validity or semantic correctness" ([mergiraf.org](https://mergiraf.org/)) — a structural merge can succeed and still be wrong. A `mergiraf review` command exists to audit its resolutions ([mergiraf.org](https://mergiraf.org/)).

The ecosystem around this layer is growing fast. jj already integrates Mergiraf as a configured merge tool, and a February 2026 discussion proposes adding **weave** — an entity-level merge driver that matches functions/classes by signature via tree-sitter across 38+ languages, claims ~95% fewer false conflicts than line-based merge on real repos (vendor benchmark), and falls back to Git's line merge for unsupported files ([jj discussion #8831](https://github.com/jj-vcs/jj/discussions/8831), [weave](https://github.com/ataraxy-labs/weave)). **gfix** (proprietary alpha) stacks the layers explicitly: Mergiraf as subprocess for structural conflicts, then an LLM for "the half mergiraf can't reach," emitting suggestions "with rationale + confidence score," and replaying accepted resolutions from `refs/gitfix/rerere/` — a rerere-style resolution ledger *stored in Git refs* ([gfix](https://www.gfix.space/)).

### The merge hierarchy

Synthesizing the above, the industry has converged — without naming it — on an escalation ladder that Multiverso should adopt as the explicit skeleton of COMPOSE:

1. **Identity/hash merge:** identical blob/tree OIDs on both sides; trivially resolved by any 3-way merge. Free.
2. **Textual merge:** diff3/ort line-based merge. Cheap; Mergiraf's own fast path ([mergiraf.org/architecture](https://mergiraf.org/architecture.html)).
3. **Structural merge:** Mergiraf/weave-class CST- or entity-level reconciliation; resolves ordering and adjacency false-conflicts; falls back to (2) when parsing fails, and may still emit conflicts ([mergiraf.org/architecture](https://mergiraf.org/architecture.html)).
4. **Agent repair:** LLM-mediated resolution with rationale and confidence (gfix's semantic layer; Multiverso's REPAIR decision) ([gfix](https://www.gfix.space/)).
5. **Oracle verification:** build/test/challenge the *merged* state regardless of which layer produced it — because layers 1–4 can all succeed on semantically conflicting changes (two candidates each pass tests alone; their textual union compiles and is wrong).
6. **Escalate:** SERIALIZE (admit one, rebase and re-verify the other) or human review.

The crucial property: **each layer's success is a claim about a weaker equivalence than the one Multiverso needs.** Only layer 5 speaks to correctness, which is why Multiverso's evidence-freshness rule — a merged state is a *new* world whose inherited receipts are stale — is not an implementation detail but the linchpin of the ladder.

### Git as the interoperability plane

What can live inside ordinary Git, per the evidence gathered here:

- **Commits/refs:** candidate world snapshots (refs under a reserved namespace), admitted trunk states, and even append-only *ledgers*: gittuf stores its Reference State Log, TUF-derived policy, and in-toto attestations entirely under `refs/gittuf/*`, so "any developer can independently verify that a repository's changes followed the expected security policies" without trusting the forge; it is an OpenSSF incubating project, in beta ([gittuf](https://github.com/gittuf/gittuf), [OpenSSF announcement](https://openssf.org/blog/2024/01/18/introducing-gittuf-a-security-layer-for-git-repositories/)). gfix's `refs/gitfix/rerere/` does the same for merge resolutions ([gfix](https://www.gfix.space/)).
- **Git notes:** attach metadata to commits without changing their hash (`refs/notes/*`), but notes "are not fetched or pushed by default," and concurrent-writer merging is manual-first with crude strategies (`union`, `cat_sort_uniq`) ([git-notes docs](https://git-scm.com/docs/git-notes)). Notes suit human-readable annotations, not a contended machine-written ledger.
- **What doesn't fit:** live conflict structure (jj needed a non-standard `jj:trees` header plus GC-guard trees ([jj git-compatibility](https://docs.jj-vcs.dev/latest/git-compatibility/))); operation logs (jj keeps its op log outside Git entirely); large evidence artifacts (logs, coverage, container images — belong in CAS with hashes referenced from in-repo attestations); mutable scheduler state and freshness/revocation, which are inherently not append-only-per-ref.

## Implications for Multiverso design

1. **Git is the admission plane; jj is (at most) an optional adapter.** Trunk admission must be an ordinary Git commit — that is non-negotiable for adoption, and jj's own architecture endorses it (Git backend is the only production backend). Do **not** build on jj-lib: pre-1.0, monthly breaking changes, no documented API stability ([docs.rs/jj-lib](https://docs.rs/jj-lib/latest/jj_lib/)). If jj integration is offered, drive the `jj` CLI in a colocated repo, and treat change-IDs as advisory (they don't survive all rewrites; forge preservation is "generally," not always ([jj git-compatibility](https://docs.jj-vcs.dev/latest/git-compatibility/))).
2. **Steal the operation-log *pattern*, not the implementation.** jj's op log demonstrates the exact semantics Multiverso's control plane needs — every mutation records a view snapshot; concurrency yields divergence, never corruption; any state is restorable ([jj op log](https://docs.jj-vcs.dev/latest/operation-log/)). But jj's op log is local, per-repo, and outside Git. Multiverso's decision ledger must be its own signed, replicated structure — with gittuf's `refs/gittuf/*` RSL as proof that a verifiable append-only log *can* ride inside Git refs and survive forge round-trips ([gittuf](https://github.com/gittuf/gittuf)).
3. **First-class conflicts are a control-plane-internal primitive.** For COMPOSE, jj proves the value of letting conflicted intermediate states exist without blocking the pipeline: the scheduler can hold a conflicted composite world, price its repair, and decide REPAIR vs SERIALIZE with full information. But conflicts must never cross the admission boundary — jj itself can only smuggle them through Git via non-standard headers that forges don't understand ([jj git-compatibility](https://docs.jj-vcs.dev/latest/git-compatibility/)). Multiverso worlds may be conflicted; ADMIT states may not.
4. **GitButler validates session→change attribution, not isolation.** The `but` model — each agent session bound to a branch, hunk-level assignment, JSON-first CLI, oplog undo — is the right *attribution* shape, and vcbench suggests interface design materially cuts agent command counts (~80% fewer commands vs git, per GitButler's own benchmark ([vcbench](https://blog.gitbutler.com/vcbench))). But virtual branches share one filesystem and app state ([GitButler docs](https://docs.gitbutler.com/ai-agents/parallel-agents)) — unusable for evidence that must be cryptographically bound to an isolated world state. Multiverso's execution plane (worktrees/containers/microVMs) is the isolation answer; GitButler's contribution is the ergonomic ledger tying agent sessions to the changes they produced.
5. **Implement COMPOSE as the explicit merge hierarchy with budget-aware escalation.** Wire Mergiraf (and optionally weave) as the structural layer via standard merge-driver interfaces — jj's `merge_tools.toml` and Git's merge drivers both work today ([jj discussion #8831](https://github.com/jj-vcs/jj/discussions/8831)). Respect its exact fallback semantics: unparseable → line-based; unsure → conflicts retained; success ≠ semantic correctness ([mergiraf.org](https://mergiraf.org/)). Every layer's output is a *new world* requiring fresh oracle evidence; no receipt inheritance across merges. Cache agent-layer resolutions gfix-style in a ref-backed rerere ledger so repeated candidate collisions are amortized ([gfix](https://www.gfix.space/)).
6. **Partition state by the Git-representability test.** In Git: world snapshot commits under reserved refs; decision records and attestations as signed, content-addressed objects in an RSL-style ref (gittuf precedent); resolution caches. Outside Git (external ledger + CAS): bulk evidence artifacts, scheduler queues, freshness clocks and revocations, cross-repo evidence. Git notes are a last resort for human-facing annotation only — unsynced by default, weak merge semantics ([git-notes](https://git-scm.com/docs/git-notes)).
7. **Which primitives genuinely help, which don't.** Help: operation-log semantics (auditability, lock-free concurrency, undo); first-class conflicts (non-blocking COMPOSE); stable change identity (tracking one candidate across repair iterations); `jj run`-style cross-change execution (oracle fan-out); hunk-level session attribution (GitButler). Irrelevant or non-transferable: auto-rebase of long descendant chains (Multiverso candidates are short-lived and re-verified anyway, though the *pattern* helps keep candidates current against a moving trunk); virtual-branch shared working dirs (wrong isolation model); Pijul's commutation (right theory, wrong ecosystem); Unison-style definition hashing (single-language premise); Fossil's everything-in-SQLite (right instinct — evidence beside code — wrong interop story).

## Open questions

- **Conflicted-world representation.** Should Multiverso define its own Git-safe encoding of N-sided conflicted composite states (as jj did with `jj:trees`), or keep conflicted states purely control-plane-internal and only ever materialize resolved trees into Git?
- **Change identity across repair.** jj's change-ID header survives amend but not rebase, and forge preservation is incomplete ([jj git-compatibility](https://docs.jj-vcs.dev/latest/git-compatibility/)). Does Multiverso need its own candidate-identity header in commits, and what is its survival contract across the agents' rewrites?
- **Benchmark validity.** vcbench measures history manipulation with raw git blocked and is vendor-published ([vcbench](https://blog.gitbutler.com/vcbench)). What would an independent benchmark of *candidate-race* substrate operations (snapshot, fork, compose, verify) look like, and does jj's slower interactive performance matter when driven headlessly by a scheduler?
- **Structural-merge false confidence.** Mergiraf retains conflicts when unsure but disclaims semantic correctness ([mergiraf.org](https://mergiraf.org/)). What fraction of structural-merge successes on agent-generated changes are semantically wrong, and can the evidence plane price that risk (e.g., mandatory adversarial challenge for L3-resolved composites)?
- **Ref-ledger scalability.** gittuf's RSL grows per ref-update ([gittuf](https://github.com/gittuf/gittuf)); Multiverso generates orders of magnitude more control-plane events (every world, oracle run, decision). Where is the cut-off between in-repo attestations and the external evidence ledger before clone/fetch costs become prohibitive?
- **jj governance as adapter risk.** jj's governance (elected maintainers, 1/3 single-company cap) reduces capture risk, but the project remains formally experimental with no 1.0 horizon announced ([jj governance](https://docs.jj-vcs.dev/latest/governance/governance/), [jj README](https://github.com/jj-vcs/jj)). What CLI-surface subset is stable enough to pin an adapter to?
