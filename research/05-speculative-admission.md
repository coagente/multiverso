# 5. Speculative Admission, Merge Queues & Evidence Freshness

> Part of the Multiverso research corpus - https://github.com/coagente/multiverso - Cutoff: 2026-08-12

## Why this matters for Multiverso

Multiverso's ADMIT decision has one non-negotiable invariant: the evidence that justifies landing a change must have been produced against **the exact integrated state that will become trunk**, not against the world where the candidate was developed. Industry has been converging on this invariant for over a decade under a different name — the merge queue, or "gating" — driven by a simple failure mode: a PR that is green on its own branch can still break trunk, because trunk moved after the PR's CI ran, or because two textually-independent changes interfere semantically. Merge queues are therefore the closest industrial ancestors of Multiverso's ADMIT regime, and they encode fifteen years of hard-won mechanism design: speculative merge states, batching and bisection, failure-driven queue resets, outcome prediction to prune speculation, and (weakly) rules for when old evidence is still valid.

They also mark the exact boundary Multiverso crosses. Every system surveyed below speculates over **orderings and groupings of independently-authored changes**; none speculates over **rival implementations of the same intent**. When a change fails gating, the universal remedy is ejection back to a human author — never substitution of an alternative candidate. Multiverso's core loop (N worlds per intent → SELECT → ADMIT) begins where every merge queue stops.

## State of the art

### The founding invariant: test the exact state that lands

The lineage runs through the Rust project's bors bots. [bors-ng](https://github.com/bors-ng/bors-ng/blob/master/README.md) implements what its documentation calls a continuous-testing workflow in which the main branch never breaks: reviewed PRs are merged into a `staging` branch (a batch is a single merge commit like `Merge #5 #7 #8`), the full test suite runs against staging, and on success **main is fast-forwarded to staging**, "guaranteeing the main branch contains only code that has been tested bit-for-bit" ([bors-ng README](https://github.com/bors-ng/bors-ng/blob/master/README.md)). This is the strongest form of exact-state admission in production use: the admitted commit *is* the tested commit, byte-for-byte. Its predecessor Homu (Rust's earlier bot) tested one PR at a time — O(N) full-suite runs — which produced day-long queues; bors-ng's batching-plus-bisection reduces this to roughly **O(E·log N)** builds, where E is the number of failing PRs ([bors-ng README](https://github.com/bors-ng/bors-ng/blob/master/README.md)). On batch failure, bors bisects: it splits the batch in two and re-queues the halves; a failing single-PR batch is "kicked back to the creator so they can fix it" — the human is the fallback, there is no alternative candidate.

### Zuul: speculative merge states across a queue

[Zuul's dependent pipelines](https://zuul-ci.org/docs/zuul/latest/gating.html) (OpenStack's gating system, in production since ~2012) generalize this to a rolling queue. For queued changes A, B, C, D, E, Zuul constructs **speculative future states**: jobs for A test A alone; jobs for B test A+B merged; jobs for E test A+B+C+D+E merged — each job runs against the state trunk *would* have if everything ahead succeeds. "It assumes that all jobs will succeed and tests them in parallel accordingly... if one fails, then changes that were expecting it to succeed are re-tested without the failed change" ([Zuul gating docs](https://zuul-ci.org/docs/zuul/latest/gating.html)). This implements nearest-non-failing-item (NNFI) semantics: if C fails while A and B pass, A and B merge and D, E restart their jobs from the new speculative tip without C. Failure is expensive — a "gate reset" cancels and restarts everything behind the failure — so Zuul throttles speculation with a TCP-like **window**: it "starts with the window set to a certain value (twenty changes by default). Each time a change successfully merges, the window is increased by one. Each time a change fails, the window is halved" ([Zuul gating docs](https://zuul-ci.org/docs/zuul/latest/gating.html)). Projects sharing a dependent-pipeline queue are tested together, so cross-project integration breakage is caught pre-merge ([Zuul gating docs](https://zuul-ci.org/docs/zuul/latest/gating.html)).

### GitHub merge queue: the mainstream implementation

GitHub's built-in merge queue (GA since 2023) creates temporary branches prefixed **`gh-readonly-queue/{base_branch}`** whose head "contains a different sha than the original pull request" — the PR's changes grouped with any PRs ahead of it plus the latest base branch ([GitHub docs: managing a merge queue](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-a-merge-queue)). CI must react to the dedicated **`merge_group`** webhook/event, distinct from `pull_request` and `push`. Tunable mechanics: "Build concurrency" (1–100 concurrent `merge_group` dispatches), "Minimum/Maximum pull requests to merge" per group, a "Wait time" for filling groups, and an "Only merge non-failing pull requests" toggle — when disabled, "pull requests that have failed required checks can be added to a group as long as the last pull request in the group has passed required checks", an explicit *weakening* of exact-state evidence for throughput ([GitHub docs: managing a merge queue](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-a-merge-queue)). On failure, "the pull request will be removed from the queue" and temporary branches behind it are recreated without it. The documented removal reasons — CI failure for a merge group, CI timeout, manual removal via API/UI, unresolvable branch-protection failure — are the closest thing the product has to an admission audit vocabulary ([GitHub docs: merging with a merge queue](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/incorporating-changes-from-a-pull-request/merging-a-pull-request-with-a-merge-queue)). Below the merge queue, plain branch protection offers a primitive freshness rule: with strict status checks "the branch **must** be up to date with the base branch before merging", and "dismiss stale pull request approvals" invalidates human review evidence when the diff changes ([GitHub docs: protected branches](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)).

Commercial queues elaborate the same design. [Aviator's parallel mode](https://docs.aviator.co/mergequeue/concepts/parallel-mode) builds "optimistic" temporary draft PRs that stack each newly queued PR on all PRs already queued; if the top draft PR fails CI, "the bot closes all subsequent Draft PRs and restarts the queue after removing the failing PR" — Zuul's reset, re-invented for GitHub.

### Chromium CQ: counterfactual evidence against flakiness

Chromium's Commit Queue is a gate rather than a queue-of-speculative-states: `CQ+1` dry-runs and `CQ+2` full-runs send the CL to a curated set of tryjobs chosen partly by which files the CL touches (`location_regexp`), and a passing full run auto-submits ([Chromium CQ docs](https://chromium.googlesource.com/chromium/src/+/HEAD/docs/infra/cq.md)). Its distinctive contribution is flake discipline: failed shards are retried with identical configuration, and the CQ then **recompiles and re-runs failing tests without the patch** — "only failing tests that break both with-patch and without-patch scenarios" are attributed to the CL ([Chromium CQ docs](https://chromium.googlesource.com/chromium/src/+/HEAD/docs/infra/cq.md)). That without-patch run is a *counterfactual receipt*: evidence about the baseline, used to avoid false attribution. Chromium accepts a residual race — the tree can move between CQ run and landing — and relies on sheriffs and reverts for post-land breakage.

### Uber SubmitQueue: probabilistic speculation, formalized

The strongest published treatment is Uber's SubmitQueue ("Keeping Master Green at Scale", [EuroSys 2019](https://dl.acm.org/doi/10.1145/3302424.3303970), author PDF at [masoud.io](https://www.masoud.io/docs/eurosys19.pdf)). Motivation numbers: before SubmitQueue, Uber's iOS mainline was green only **52%** of the time, and with just 16 concurrent pending changes there was a ~40% probability of conflict ([The Morning Paper summary](https://blog.acolyer.org/2019/04/18/keeping-master-green-at-scale/)). The system builds a **speculation tree** — a binary decision tree over pending changes where each node is a possible build (change Cᵢ lands / fails), edges annotated with predicted probabilities — and spends its parallel build capacity only on the most probable root-to-leaf paths. Probabilities come from a **logistic regression over ~100 hand-picked features** reaching ~97% accuracy (strong positive signals: prior successful speculations, presence of test plans; negative: failed speculations, resubmissions). A **conflict analyzer** checks whether pending changes share build targets; target-disjoint changes commute and can be verified and landed independently, turning the tree into a forest and preserving *serializability* — trunk always equals the result of some sequential order of landed changes. Reported results: mainline green ~100% of the time since introduction, with turnaround ≈1.2× a perfect-prediction oracle ([The Morning Paper](https://blog.acolyer.org/2019/04/18/keeping-master-green-at-scale/)).

Uber kept evolving the shipped system. **BLRD** ("Bypassing Large Diffs", [Uber blog, Aug 31 2023](https://www.uber.com/en-CA/blog/bypassing-large-diffs-in-submitqueue/)) lets a small change land *out of order* ahead of a big blocking change **iff all its paths in the speculation tree have been verified and all paths agree on the outcome** — i.e., its result is invariant to whether the big change lands — yielding a 74% improvement in land wait time while keeping trunk green. In 2025 Uber replaced parts of the probabilistic model with **NGBoost** models that predict both build success and build-time distributions, plus a speculation threshold that only builds the most probable nodes: builds-per-change fell 45–64%, CPU 35–52%, P95 wait times 31–44% — "slash CI resource usage by 53% and speed up wait times by 37% — all while keeping mainlines green" ([Slashing CI Costs at Uber, Jun 23 2025](https://www.uber.com/blog/slashing-ci-costs-at-uber/)). SubmitQueue was open-sourced as [uber/submitqueue](https://github.com/uber/submitqueue/) (Apache 2.0), described as "a high-performance speculative merge queue that keeps your trunk consistently green at scale" that "speculatively rebases and validates multiple changes in parallel against predicted future states of HEAD". Academia is following: a 2025 ICSME industry-track paper shows learned PR ordering (prioritizing likely-passing PRs during peak hours) significantly outperforms FIFO in merge pipelines ([Jungwirth, Gruber & Fraser, arXiv:2508.08342, Aug 2025](https://arxiv.org/abs/2508.08342)).

### Evidence reuse vs re-run: when is cached evidence still valid?

Merge queues answer "what state to test"; a second body of work answers "which past results still count". There is a hard line between **sound** reuse and **probabilistic** reuse:

- **Sound-by-construction (content-addressed action caching).** Bazel's remote cache is an action cache ("a map of action hashes to action result metadata") plus a CAS of output files; an action's key covers its declared inputs, output names, command line, and only environment variables explicitly whitelisted via `--action_env` ([Bazel remote caching docs](https://bazel.build/remote/caching)). After a rebase, any action whose transitive input digests are unchanged gets a cache hit — its old result is *valid by construction* for the new integrated state. Validity fails exactly where hermeticity fails: Bazel "does not track tools outside a workspace", so untracked toolchains or unpinned env vars poison keys, which is why the docs warn to "take care in who has the ability to write to the remote cache" ([Bazel remote caching docs](https://bazel.build/remote/caching)). This is per-action evidence freshness, mechanized.
- **Sound-by-dependency (safe regression test selection).** [Ekstazi](https://github.com/gliga/ekstazi) (Gligoric, Eloussi & Marinov, ISSTA 2015) records the dynamic *file* dependencies of each test and skips a test after a change iff none of its recorded dependencies changed — a safety guarantee at file granularity, coarser than Bazel's action keys but requiring no build-graph purity.
- **Probabilistic (learned test selection).** Meta's **predictive test selection** trains gradient-boosted decision trees on historical outcomes to pick, per change, the tests most likely to fail: it "reduces the total infrastructure cost of testing code changes by a factor of two, while guaranteeing that over 95% of individual test failures and over 99.9% of faulty changes are still reported", running about a third of the tests that transitively depend on modified code ([Machalica et al., arXiv:1810.05286](https://arxiv.org/abs/1810.05286), ICSE-SEIP 2019; [Meta engineering blog, Nov 2018](https://engineering.fb.com/2018/11/21/developer-tools/predictive-test-selection/)). [Launchable](https://help.launchableinc.com/features/predictive-test-selection/) commercialized the same idea, with "defensive runs" of the unselected remainder to keep the model honest.
- **Batching under resource ceilings (Google TAP).** Google's Test Automation Platform gates a ~2-billion-LOC monorepo where "TAP integrates and tests... more than 13K code projects, requiring 800K builds and 150 Million test runs" per day (2016 data); unable to test every commit, it cuts **milestones** roughly every 45 minutes, batching all commits since the last cut and running only build-graph-affected targets — milestones as large as 4.2M tests, with observed feedback delays up to 9 hours ([Memon et al., Taming Google-Scale Continuous Testing, ICSE-SEIP 2017](https://research.google.com/pubs/archive/45861.pdf)). The same paper's key statistics motivate selection: of 5.5M affected test targets over a month, only ~63K ever failed; only **1.23%** of executions found a real breakage or fix; targets more than 10 dependency edges from the change "hardly ever break". The SWE-at-Google account adds the trunk-repair side: presubmits take ~11 minutes and predict ~95%+ of downstream success; postsubmit TAP batches, bisects failing batches per-change for culprit finding, and "has been upgraded to automatically roll back changes when it has high confidence that they are the culprit" ([Software Engineering at Google, ch. 23](https://abseil.io/resources/swe-book/html/ch23.html)).

### The gap between "correct in its world" and "safe on current trunk"

Merge queues exist because textual merge is not a semantic oracle. The literature distinguishes **textual conflicts** ("the merge fails to produce code") from **semantic conflicts** ("the merged code results in compiler or test breaks") ([Zhang et al., ISSTA 2022 / arXiv:2111.11904](https://arxiv.org/abs/2111.11904)). Classic instances: one branch changes a method signature while another adds a call site with the old signature (clean merge, broken build), or two branches touch shared state with clean text and broken behavior. Detection research spans variability-aware execution ([Nguyen et al., FSE 2015](https://dl.acm.org/doi/10.1145/2786805.2803208)), static interference analysis — better F1/recall than dynamic approaches on 99 merge-scenario units ([Santos de Jesus, Borba et al., arXiv:2310.04269, Oct 2023](https://arxiv.org/abs/2310.04269)) — and automatically generated unit tests at integration points ([Detecting semantic conflicts with unit tests, JSS 2024](https://www.sciencedirect.com/science/article/pii/S0164121224001158)). Uber's 52%-green iOS mainline *despite per-change CI* is the production face of the same gap ([The Morning Paper](https://blog.acolyer.org/2019/04/18/keeping-master-green-at-scale/)). The merge queue closes it only to the strength of the gate's test suite: semantic interference invisible to the gate's oracles still lands, which is why Google backs its gate with comprehensive postsubmit cycles, culprit finding, and auto-rollback ([SWE at Google, ch. 23](https://abseil.io/resources/swe-book/html/ch23.html)).

### Rollback and audit trails

Existing systems handle "we admitted a bad change" operationally, not cryptographically. Google's TAP auto-rolls-back high-confidence culprits and staffs "Build Cops" ([SWE at Google, ch. 23](https://abseil.io/resources/swe-book/html/ch23.html)); Chromium relies on revert culture plus the CQ's with/without-patch attribution ([Chromium CQ docs](https://chromium.googlesource.com/chromium/src/+/HEAD/docs/infra/cq.md)); GitHub's merge queue logs enumerable removal reasons ([GitHub docs](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/incorporating-changes-from-a-pull-request/merging-a-pull-request-with-a-merge-queue)). But none of them emits a signed, replayable record binding *this evidence* to *this exact integrated tree* under *this policy* — the artifact trail is CI logs and status checks keyed to SHAs, disconnected from decision rationale. The supply-chain world builds exactly such bindings for build provenance ([SLSA](https://slsa.dev)), but no merge-queue product connects admission decisions to attestation frameworks today.

### Confirming the key question: no queue selects among alternatives

Across every system above, the unit of speculation is an **independently-authored change**. Zuul speculates over queue orderings; bors-ng over batch compositions; GitHub over merge groups; SubmitQueue's speculation tree branches over *pass/fail outcomes* of distinct changes — never over rival payloads for the same intent. Failure handling confirms it: Zuul ejects and re-tests the remainder ([Zuul gating docs](https://zuul-ci.org/docs/zuul/latest/gating.html)); GitHub removes the PR ([GitHub docs](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-a-merge-queue)); bors kicks the PR "back to the creator" ([bors-ng README](https://github.com/bors-ng/bors-ng/blob/master/README.md)). There is no SELECT stage anywhere in this design space; the queue's contract is *serialize independent changes safely*, and the generation of the change itself is out of scope. Multiverso's ADMIT is a merge queue whose enqueued item is not "a PR" but "the winner of an evidence-driven tournament among N worlds" — and whose gate evidence carries freshness classes rather than a binary status check.

## Implications for Multiverso design

1. **Admit the tested tree, not a re-merge of it.** bors-ng's fast-forward-to-staging is the gold standard: the attestation should bind evidence to the *tree hash of the integrated state I = merge(trunk@t, world Δ)*, and admission should make trunk equal exactly that tree. Any design where the landing step re-performs the merge (Zuul/Gerrit-style, Chromium-style) reintroduces a race the attestation cannot cover.
2. **Make evidence freshness a typed lattice, not a boolean.** The survey yields three natural validity classes after trunk moves: (a) *sound-by-construction* — a Bazel-style action-cache hit whose transitive input digests are unchanged in I ([Bazel](https://bazel.build/remote/caching)); (b) *sound-by-dependency* — Ekstazi-style: the rebase delta is disjoint from the test's recorded dependency closure ([Ekstazi](https://github.com/gliga/ekstazi)); (c) *probabilistic* — a model says re-running is unlikely to change the verdict ([Meta PTS](https://arxiv.org/abs/1810.05286)). Multiverso receipts should carry their class, and admission policy should state which classes are acceptable per oracle (e.g., class (c) never sufficient for the final ADMIT gate, always sufficient for early world-pruning).
3. **Steal SubmitQueue's planner for the budget question.** Multiverso's core research question — evidence-aware allocation under a fixed budget — already has a production sibling: SubmitQueue's speculation tree with learned success/build-time prediction cut CI resources 53% while keeping trunk green ([Uber 2025](https://www.uber.com/blog/slashing-ci-costs-at-uber/)). Multiverso's scheduler generalizes the tree in two dimensions: nodes are (world × oracle) pairs rather than (change × build), and siblings are *rivals* rather than independents — so pruning can be more aggressive (only one sibling can win SELECT).
4. **BLRD's invariance trick is a commutativity proof — reuse it.** "All speculation paths verified and all agree" ([Uber BLRD](https://www.uber.com/en-CA/blog/bypassing-large-diffs-in-submitqueue/)) is exactly the certificate Multiverso needs to admit a small intent's winner out of order while a big intent is still under challenge, and to decide COMPOSE vs SERIALIZE for winners of different intents.
5. **Adopt adaptive-window admission control.** Zuul's window (start 20, +1 on success, halve on failure) is congestion control for speculation cost ([Zuul](https://zuul-ci.org/docs/zuul/latest/gating.html)). Multiverso should apply the same additive-increase/multiplicative-decrease shape to how many worlds it integrates speculatively above trunk, priced against the evidence budget.
6. **Counterfactual receipts, from Chromium.** The CQ's without-patch re-run ([Chromium](https://chromium.googlesource.com/chromium/src/+/HEAD/docs/infra/cq.md)) should be a first-class receipt type: a failure only counts against a world if the baseline (trunk or the integrated state minus this Δ) passes the same oracle. This simultaneously handles flakiness and mis-attribution in COMPOSE decisions.
7. **Semantic-conflict oracles belong in the ADMIT challenge budget.** Textual-clean merges still break builds and behavior ([ISSTA 2022](https://arxiv.org/abs/2111.11904)); static interference analysis and targeted test generation at integration points ([arXiv:2310.04269](https://arxiv.org/abs/2310.04269), [JSS 2024](https://www.sciencedirect.com/science/article/pii/S0164121224001158)) are cheap adversarial probes to run specifically on the *merge delta* between world and trunk — the region no candidate-side evidence covers.
8. **Close the audit gap.** No surveyed system emits a signed attestation binding (trunk parent, world snapshot, integrated tree, receipts + freshness classes, decision, policy version). GitHub's removal-reason vocabulary ([docs](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/incorporating-changes-from-a-pull-request/merging-a-pull-request-with-a-merge-queue)) and TAP's auto-rollback ([SWE book](https://abseil.io/resources/swe-book/html/ch23.html)) are the operational fragments; binding them into a SLSA-style provenance object ([SLSA](https://slsa.dev)) at the *admission* (not build) layer is genuinely novel territory and Multiverso's cheapest differentiation.
9. **Budget for gate resets.** Every system pays heavily for late failure (Zuul window halving, Aviator queue restarts, GitHub group rebuilds). Because Multiverso runs adversarial challenge *before* enqueueing, its admission-queue failure rate should be engineered low and monitored as a first-class metric — a high reset rate means SELECT is passing junk forward and the budget split is wrong.

## Open questions

- **Formal freshness bounds.** Under continuous admission of sibling intents, how stale can class-(b)/(c) evidence be before false-admission risk exceeds policy? Is there a useful analytic model linking trunk churn rate, dependency-closure overlap, and re-run probability (the Memon et al. data — 1.23% of executions finding real breakage, distance-10 targets "hardly ever break" — suggests the risk is extremely skewed and exploitable)?
- **Conflict analysis for AI-generated changes.** SubmitQueue's target-level conflict analyzer assumes changes have legible build-target footprints. Do LLM-authored changes (broader, more incidental edits) erode the independence assumption that makes speculation forests cheap?
- **Flaky oracles as poisoned training data.** Merge queues fight flakiness for throughput; Multiverso additionally trains its scheduler on receipts. What quarantine discipline prevents flaky evidence from corrupting both admission decisions *and* the learned allocation policy?
- **Multi-winner admission.** When winners of several intents are ready simultaneously, is the right structure a Zuul-style shared queue over winners, a SubmitQueue-style speculation forest with rival-aware pruning, or pairwise BLRD-style invariance checks feeding COMPOSE?
- **Attestation grammar for reused evidence.** What does a "proof-carrying cache hit" look like — an attestation that cites a *prior* attestation plus a soundness argument (unchanged input digests / disjoint dependency closure) instead of a fresh execution receipt — and can verifiers check it without trusting the cache operator ([Bazel's ACL-trust model](https://bazel.build/remote/caching) is explicitly weaker)?
