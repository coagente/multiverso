# 18. Forge Integration: GitHub-First Admission Surface

> Part of the Multiverso research corpus - https://github.com/coagente/multiverso - Cutoff: 2026-08-12

## Why this matters for Multiverso

Multiverso's ADMIT decision must terminate in an ordinary Git commit on trunk plus a signed attestation — and for the overwhelming majority of target teams, trunk lives on GitHub behind branch protection, required checks, and (increasingly) a merge queue. The admission gate is only real if GitHub's own enforcement primitives make it unbypassable: a check run that a ruleset requires, pinned to Multiverso's App identity, so no human or rogue integration can green-light a merge by spoofing the context. This chapter maps exactly which GitHub surfaces exist for (1) painting the admission verdict on a PR, (2) surviving the merge queue's speculative merge state, (3) storing candidate worlds and receipts in the repo itself, and (4) anchoring attestations — and derives a two-stage integration design: an App-less v0 (pure git + local CLI) and a GitHub App v1 with exact permissions, events, and rate-limit budgets.

## State of the art

### (a) The GitHub App model: the only door into the Checks API

**Checks are App-gated.** The Checks REST API states flatly: "Write permission for the REST API to interact with checks is only available to GitHub Apps" — OAuth apps and PATs can read check runs but never create them ([Check Runs API](https://docs.github.com/en/rest/checks/runs?apiVersion=2022-11-28)). This single constraint forces the v0/v1 split: any rich, annotated, button-bearing admission gate requires shipping a GitHub App.

**Permissions Multiverso needs.** GitHub App permissions are granted per-installation as repository/organization/enterprise-scoped read/write grants ([choosing permissions](https://docs.github.com/en/apps/creating-github-apps/registering-a-github-app/choosing-permissions-for-a-github-app)). The permissions reference confirms the relevant repository permissions exist as distinct grants: **Checks** (write unlocks `POST /repos/{owner}/{repo}/check-runs` and `PATCH .../check-runs/{id}`), **Commit statuses** (write unlocks `POST /repos/{owner}/{repo}/statuses/{sha}`), **Contents**, **Pull requests**, **Workflows**, and — importantly for §(e) — a dedicated **Attestations** repository permission with read and write endpoints ([permissions required for GitHub Apps](https://docs.github.com/en/rest/authentication/permissions-required-for-github-apps?apiVersion=2022-11-28)). Webhook subscriptions ride on permissions: `push` needs at least read on **Contents**; `check_run`/`check_suite` need read on **Checks** (write to receive `requested_action`); `pull_request` needs read on **Pull requests**; `merge_group` needs "at least read-level access for the 'Merge queues' repository permission" ([webhook events and payloads](https://docs.github.com/en/webhooks/webhook-events-and-payloads)).

**Tokens.** The App authenticates with a JWT, then mints an installation access token via `POST /app/installations/{id}/access_tokens`; the token "will expire after 1 hour" and can be down-scoped at mint time via `repositories`/`repository_ids` and `permissions` body parameters. The same token drives git-over-HTTPS: `git clone https://x-access-token:TOKEN@github.com/owner/repo.git` (requires Contents) ([authenticating as an installation](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/authenticating-as-a-github-app-installation)). Deploy keys are the wrong tool: they "only grant access to a single repository", have no expiry, survive the removal of the user who created them, and grant no REST API access; GitHub's own docs recommend "using a GitHub App instead" ([managing deploy keys](https://docs.github.com/en/authentication/connecting-to-github-with-ssh/managing-deploy-keys)).

**Rate limits per installation.** Primary: 5,000 requests/hour baseline; "Installations that have more than 20 repositories receive another 50 requests per hour for each repository. Installations that are on an organization that have more than 20 users receive another 50 requests per hour for each user. The rate limit cannot increase beyond 12,500 requests per hour" — and 15,000/hour flat for installations on GitHub Enterprise Cloud organizations. The binding constraint for Multiverso is secondary limits: "No more than 100 concurrent requests", 900 points/minute per REST endpoint family (writes cost 5 points), and **"80 content-generating requests per minute and no more than 500 content-generating requests per hour"** ([REST rate limits](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api?apiVersion=2022-11-28)). Every check-run create/update, status post, comment, and attestation upload is a content-generating request — this caps how chatty a live race dashboard can be (see budget math below).

### (b) The Checks API as the "Multiverso admission gate"

A check run is the natural projection of an admission decision onto a PR:

- **Lifecycle**: `status` ∈ `queued`, `in_progress`, `completed` (plus `waiting`/`requested`/`pending`); `conclusion` ∈ `success`, `failure`, `neutral`, `cancelled`, `skipped`, `timed_out`, `action_required`; setting `conclusion` in a `PATCH` auto-completes the run ([Check Runs API](https://docs.github.com/en/rest/checks/runs?apiVersion=2022-11-28)).
- **Evidence rendering**: `output.title` / `output.summary` / `output.text` (markdown, 64 KB max), inline file **annotations** capped at "a maximum of 50 per API request" (append more with further PATCHes), and images with `image_url` — enough to render the race table (N candidates × oracle verdicts) directly in the PR's Checks tab, with `details_url` deep-linking to the full receipt viewer.
- **Action buttons**: "A maximum of three actions are accepted", each with `label` (≤20 chars), `description` (≤40), `identifier` (≤20); clicking one fires a `check_run` webhook with `requested_action` to Apps holding Checks write ([Check Runs API](https://docs.github.com/en/rest/checks/runs?apiVersion=2022-11-28), [webhook events](https://docs.github.com/en/webhooks/webhook-events-and-payloads)). Multiverso's three: `re-race`, `repair`, `explain`.
- **Enforcement + anti-spoofing**: a ruleset's "Require status checks to pass" rule lets you "select an app as the expected source of status updates… If the status is set by any other person or integration, merging won't be allowed" ([available rules for rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets)). Pinning the `multiverso/admission` context to the Multiverso App's integration ID is what turns the check run into an actual gate rather than a suggestion.

The **Commit Statuses API** is the older, weaker sibling — but it is *not* App-gated: "Users with push access in a repository can create commit statuses for a given SHA" via `POST /repos/{owner}/{repo}/statuses/{sha}` with `state` ∈ `error|failure|pending|success`, a `context` label, `target_url`, and `description`; note "a limit of 1000 statuses per sha and context" ([Commit statuses API](https://docs.github.com/en/rest/commits/statuses?apiVersion=2022-11-28)). A fine-grained PAT with Commit statuses write is therefore the v0.5 path to a *required*, ruleset-enforceable gate without shipping an App — at the cost of no annotations, no buttons, no markdown.

### (c) Merge queue interplay: the freshness problem GitHub already forces on you

GitHub's merge queue builds speculative merge commits on temporary branches with "the special prefix `gh-readonly-queue/{base_branch}`" and requires CI to react to the queue, not the PR: "if your repository uses GitHub Actions" and workflows only trigger on `pull_request`, "status checks will not be triggered when you add a pull request to a merge queue. The merge will fail" ([managing a merge queue](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-a-merge-queue)). Third-party systems subscribe to the **`merge_group`** webhook (actions `checks_requested` and `destroyed`; requires Merge queues read), and the docs are explicit about the contract: "When you receive this event, you should perform checks on the head SHA and report status back using check runs or commit statuses" ([webhook events](https://docs.github.com/en/webhooks/webhook-events-and-payloads)). In Actions terms, `GITHUB_SHA` is the "SHA of the merge group" and `GITHUB_REF` the "Ref of the merge group", and `merge_group` supports only the `checks_requested` activity type ([events that trigger workflows](https://docs.github.com/en/actions/writing-workflows/choosing-when-your-workflow-runs/events-that-trigger-workflows#merge_group)). The queue has a configurable "Status check timeout" after which it assumes checks failed, and merge queue can be required either via branch protection ("Require merge queue") or via a repository ruleset rule (public beta since Feb 2024; not available in org rulesets at launch) ([managing a merge queue](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-a-merge-queue), [changelog](https://github.blog/changelog/2024-02-27-repository-rules-configure-merge-queue-rule-public-beta/)).

This is a gift to Multiverso's thesis: the merge-group head SHA is *by construction a different tree* than the PR head the race verified, so every receipt bound to the candidate's world state is formally stale inside the queue. GitHub thus already forces the evidence-freshness question that chapter 5 typed. Multiverso's queue behavior should be: on `merge_group.checks_requested`, fetch the merge-group head, compute the delta vs. the admitted candidate tree, and either (i) re-run the cheap freshness-oracle tier and emit a fresh receipt bound to the merge-group SHA, or (ii) attest a sound-by-dependency carry-over (no overlapping impact set) — then complete a check run *on that SHA* within the queue timeout.

### (d) Representing a candidate race on GitHub: refs, PRs, and what survives

**Custom ref namespaces work; the UI ignores them; rulesets can't protect them.** Git itself permits arbitrary namespaces, and default fetch refspecs only cover `refs/heads/*` and `refs/tags/*` ([the refspec](https://git-scm.com/book/en/v2/Git-Internals-The-Refspec)). GitHub accepts pushes to non-standard namespaces in practice — GitButler ships exactly this pattern, storing one real ref per virtual branch "under the `refs/gitbutler/` namespace", which users can inspect and push (e.g. `git push origin refs/gitbutler/X:refs/heads/Y`) ([GitButler push and fetch](https://docs.gitbutler.com/features/virtual-branches/pushing-and-fetching), [virtual branches](https://docs.gitbutler.com/features/virtual-branches/virtual-branches)). Two hard exceptions: the "`refs/pull/` namespace is *read-only*" — pushes to it are rejected as updates to hidden refs ([checking out PRs locally](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/reviewing-changes-in-pull-requests/checking-out-pull-requests-locally), [community discussion #124685](https://github.com/orgs/community/discussions/124685)); and ruleset restrict-creation/update/deletion rules target only "branches or tags whose name matches the pattern" — custom namespaces like `refs/multiverso/*` cannot be write-protected by rulesets ([available rules](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets)). Consequence: anyone with push access can overwrite `refs/multiverso/*`, so **receipts must be self-authenticating (signed, content-addressed), never location-authenticated**. Whether GitHub imposes undocumented server-side limits (ref-count performance, GC of objects reachable only from custom refs) is not officially documented (unverified); mirroring evidence refs to a Multiverso-controlled remote is the hedge.

**Git notes are pushable but dead on GitHub.** GitHub displayed `refs/notes/commits` on commit pages from 2010 ([Git Notes Display](https://github.blog/news-insights/git-notes-display/)) until August 2014, when display support was removed; notes can still be pushed and fetched but are invisible in the UI and absent from the API, and the request to restore them remains an open community discussion ([Bring back git notes!](https://github.com/orgs/community/discussions/154991), [Git Notes: git's coolest, most unloved feature](https://lobste.rs/s/vmrnyd/git_notes_git_s_coolest_most_unloved)). Verdict: notes are acceptable as an *optional mirror* of receipt digests for git-native tooling, never the primary channel.

**Race representation options.** (1) *N draft PRs* — maximal UI visibility, but N× check-suite noise, N× webhook fan-out, and PR-number pollution; (2) *N branches under `refs/heads/mv/…`* — visible, but pollutes branch lists and triggers CI everywhere; (3) **candidates under `refs/multiverso/intent/<id>/cand/<n>` + exactly one PR carrying the winner** — candidates stay fetchable (`git fetch origin '+refs/multiverso/*:refs/multiverso/*'`), invisible to normal users, cost nothing in CI, and losers are deleted (or retained as evidence) without ceremony. The winner is pushed to a normal branch and opened as the PR; a superseding winner is a force-push to that same branch (the PR follows), with the check run re-created on the new head SHA. This is the recommended design.

### (e) Attestations: GitHub's store is now writable outside Actions — but `gh verify` isn't the verifier for you

GitHub artifact attestations are Sigstore bundles over in-toto statements: "cryptographically signed claims that establish your build's provenance"; public repos sign via the **Sigstore Public Good Instance** (with a public transparency log), private repos via "GitHub's Sigstore instance", which "does not have a transparency log and only federates with GitHub Actions"; attestations alone give "SLSA v1.0 Build Level 2", Level 3 with reusable workflows ([artifact attestations concept](https://docs.github.com/en/actions/concepts/security/artifact-attestations)).

The REST surface as of the current API version:

- **Write**: `POST /repos/{owner}/{repo}/attestations` stores a bundle (`mediaType`, `verificationMaterial`, `dsseEnvelope`) and needs the fine-grained `attestations:write` permission — which GitHub Apps can hold ([attestations API](https://docs.github.com/en/rest/repos/attestations?apiVersion=2022-11-28), [App permissions](https://docs.github.com/en/rest/authentication/permissions-required-for-github-apps?apiVersion=2022-11-28)). So **yes: an App or a fine-grained-PAT CLI can upload attestations without Actions**.
- **Read**: `GET /repos/{owner}/{repo}/attestations/{subject_digest}` with `subject_digest` as `sha256:HEX`, optional `predicate_type` filter, `per_page` max 100 ([attestations API](https://docs.github.com/en/rest/repos/attestations?apiVersion=2022-11-28)).
- **CLI**: `gh attestation` exposes only `download`, `verify`, and `trusted-root` — there is **no upload verb**; writes go through REST ([gh attestation](https://cli.github.com/manual/gh_attestation)).

The catch is verification policy: `gh attestation verify` defaults the OIDC issuer to `https://token.actions.githubusercontent.com` and validates the certificate's SourceRepository/SourceRepositoryOwner/SAN — i.e., it assumes the attestation was signed inside GitHub Actions ([gh attestation verify](https://cli.github.com/manual/gh_attestation_verify)). A Multiverso attestation signed outside Actions (its own DSSE key, or a public-good Fulcio identity) will upload fine but will not pass stock `gh attestation verify`; and for **private repos**, GitHub's Sigstore instance "only federates with GitHub Actions", so non-Actions signing can't use GitHub's CA at all ([artifact attestations concept](https://docs.github.com/en/actions/concepts/security/artifact-attestations)). Therefore: canonical receipts live in git (portable, forge-neutral, verified by `mv verify` / cosign with Multiverso's trust root); the GitHub attestations store is a *mirror* keyed by `sha256:` digests of the receipt bundle and admitted tree; a self-hosted Rekor is deferred until customers demand an independent transparency log (public repos get the public-good log for free).

### (f) Webhooks for trunk-movement detection

Evidence-freshness invalidation needs to observe trunk. The `push` event (Contents read) carries exactly the needed fields: `ref` ("The full git ref that was pushed"), `before`/`after` SHAs, `forced`, `deleted`, `created`, and the `commits` array ([webhook events](https://docs.github.com/en/webhooks/webhook-events-and-payloads)). On `push` to `refs/heads/main`: recompute impact overlap between `before..after` and every open world's dependency set; downgrade sound-by-dependency receipts whose basis moved; flag `forced` pushes as full invalidation. Delivery is best-effort: "Your server should respond with a 2XX response within 10 seconds", and missed deliveries must be actively redelivered ("If your server goes down, you should redeliver missed webhooks once your server is back up") ([webhook best practices](https://docs.github.com/en/webhooks/using-webhooks/best-practices-for-using-webhooks)). Treat webhooks as latency-reducing hints over a poll-based reconciler (`git fetch` + merge-base comparison), never as the source of truth.

**GitLab / Gitea (secondary notes).** GitLab's analogue to a required third-party gate is **external status checks** (Ultimate tier only): GitLab POSTs a merge-request webhook to the external service, which answers via the status-check response API; "Status checks must succeed" can block merge, responses not matching the current source-branch HEAD get `409 Conflict`, and checks pending beyond the documented window are failed ([GitLab status checks](https://docs.gitlab.com/user/project/merge_requests/status_checks/)). On the commodity tier, the pipeline/commit-status API is the fallback. Gitea has no Checks API — only commit statuses — but its **AGit flow** (since Gitea 1.13, server git ≥ 2.29) is directly relevant to candidate representation: pushing `HEAD:refs/for/master -o topic=test` creates a PR from a ref push without any branch ([Gitea AGit](https://docs.gitea.com/usage/agit)), a cleaner server-side candidate-ingestion primitive than anything GitHub offers. Design the forge adapter interface around three verbs — `paint_gate(sha, verdict)`, `ingest_candidate(ref)`, `observe_trunk()` — and both forges slot in.

## Recommendation for the PRD

**v0 — App-less, pure git + local CLI (`mv`).** No server, no webhooks, no GitHub API. Worlds are local worktrees; candidates optionally published to `refs/multiverso/intent/<uuid>/cand/<n>`; receipts are DSSE-signed, content-addressed files under `refs/multiverso/evidence/<intent>` (self-authenticating because the namespace is unprotectable); admission = `mv admit` fast-forwards the winner onto `main` (or opens a PR via `gh pr create`), embedding the receipt-bundle digest in the commit message trailer (`Multiverso-Receipt: sha256:…`). Freshness is polled: `git fetch` + merge-base drift. This works against GitHub, GitLab, Gitea, and bare remotes identically — it is the vendor-neutral core and must never grow a GitHub dependency.

**v0.5 — PAT statuses (optional, 1 week of work).** A fine-grained PAT with Commit statuses write posts `context: multiverso/admission` (`pending` → `success|failure`) on the PR head; the repo makes it required. Buys enforceability with zero App infrastructure; accept that without App-pinning the context is spoofable by anyone with push access.

**v1 — the Multiverso GitHub App.** Manifest: repository permissions `contents:write`, `checks:write`, `pull_requests:write`, `statuses:write`, `attestations:write`, `merge_queues:read`; events `push`, `pull_request`, `check_run`, `check_suite`, `merge_group`. One check run `multiverso/admission` per PR head: `queued` at intent registration, `in_progress` during the race with the candidate×oracle table in `output.summary`, completed with `success` (ADMIT), `failure` (REJECT), `neutral` (SERIALIZE/withdrawn), or `action_required` (REPAIR proposed) and buttons `re-race` / `repair` / `explain` handled via `requested_action`. Enforce with a ruleset requiring the check *with the App pinned as expected source*. Subscribe `merge_group` from day one and complete a freshness check run on the merge-group head SHA within the queue's status-check timeout. **Rate budget**: one race ≈ 1 check-run create + ≤10 PATCHes (throttle live updates to ~1/min) + 1 attestation POST + a handful of reads ⇒ ~12 content-writes; the 500 content-writes/hour secondary cap therefore bounds ~40 concurrent races/hour/installation — enforce a client-side token bucket and degrade to fewer PATCHes, never risk a completed-conclusion write being throttled. Attestations: dual-write (canonical in-git receipt; mirror bundle to `POST /repos/{owner}/{repo}/attestations` keyed by tree and receipt digests); verification is `mv verify` (cosign-compatible), with `gh attestation verify` supported only for the optional Actions-resident signing mode.

**Do not build**: N draft PRs per race; git-notes-primary evidence; deploy-key auth; any design requiring pushes to `refs/pull/*`.

## Open questions

1. **Custom-ref durability at scale**: GitHub documents no limits on non-branch namespaces (ref-count performance, GC of objects only reachable from `refs/multiverso/*`, Enterprise policy blocks). Needs empirical probing before racing 50-candidate intents on large monorepos (unverified).
2. **Attestation-store acceptance policy**: whether `POST /repos/{owner}/{repo}/attestations` validates the bundle's certificate chain against GitHub/public-good roots or accepts any well-formed DSSE bundle (i.e., can Multiverso's self-signed bundles live there for private repos?) is not stated in the API docs (unverified) — prototype in week 1.
3. **Merge-queue third-party latency**: the queue's status-check timeout vs. realistic freshness-oracle runtimes; whether a `neutral`-then-`success` two-phase report keeps the group alive (unverified).
4. **Org-ruleset coverage**: merge-queue-as-ruleset was repo-level public beta at launch ([changelog](https://github.blog/changelog/2024-02-27-repository-rules-configure-merge-queue-rule-public-beta/)); current org-level availability needs re-checking at build time.
5. **`merge_group` payload field inventory** (`head_sha`, `head_ref`, `base_sha`, …) is not enumerated in the rendered webhook docs; confirm against the OpenAPI/octokit schema during implementation (the contract quote — "perform checks on the head SHA" — is verified).
